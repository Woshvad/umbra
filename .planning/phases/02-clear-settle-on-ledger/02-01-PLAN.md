    Define `data OrderView = OrderView with desk : Party; side : Side; quantity : Int; limit : Decimal deriving (Eq, Show)` — a flat view decoupled from the `Order` template so the math is a pure function of plain data (mirrorable in TS, Phase 4).

    Implement, exactly per spec §8:
    - `isBuy`, `isSell` predicates on `OrderView`.
    - `demandAt : [OrderView] -> Decimal -> Int` = Σ quantity of buys with `limit >= p` (§8 step 2).
    - `supplyAt : [OrderView] -> Decimal -> Int` = Σ quantity of sells with `limit <= p` (§8 step 2).
    - `matchedAt : [OrderView] -> Decimal -> Int` = `min (demandAt orders p) (supplyAt orders p)`.
    - `candidatePrices : [OrderView] -> [Decimal]` = `sort (dedup [ o.limit | o <- orders ])` (§8 step 1: distinct, sorted).
    - `choosePStar : [OrderView] -> Decimal` (§8 step 3, THE tie-break trap — per 02-CONTEXT phase_critical_constraint 1): compute `matches = [ (p, matchedAt orders p) | p <- candidatePrices orders ]`; `maxMatched = foldl max 0 [ m | (_, m) <- matches ]` (use `foldl max 0`, NOT `maximumBy` — empty-list safety for a no-cross round, per RESEARCH Pitfall 4); `topPrices = [ p | (p, m) <- matches, m == maxMatched ]` (this filter to the max-matched subset is the trap-guard); then `ranked = sortOn (\p -> (abs (demandAt orders p - supplyAt orders p), p)) topPrices` (the `(imbalance, price)` tuple's lexicographic Ord encodes tie-break (a) minimize |demand−supply| THEN (b) lower price, applied ONLY over topPrices); return the head of `ranked`, or `0.0` if empty (no-cross; caller guards).
    - `rationByPriority : [OrderView] -> Int -> [(OrderView, Int)]` (§8 step 4 long-side rationing): greedy fill most-aggressive-first over an already-ordered list — `go [] _ = []`; `go (o :: rest) remaining = let f = min o.quantity remaining in (o, f) :: go rest (remaining - f)`. Document the leftover-to-largest rule for equal-limit ties in a comment (it does NOT trigger on §4 — no equal-limit tie — but must match the future TS impl, per RESEARCH A3).
    - `computeClearing : [OrderView] -> (Decimal, [Allocation])` (§8 step 4–5): `pStar = choosePStar orders`; `traded = matchedAt orders pStar`; `buys = [ o | o <- orders, isBuy o, o.limit >= pStar ]` sorted DESCENDING by limit (most-aggressive buy first — use `sortOn (\o -> negate o.limit) buys` or a descending comparator; the bare `negate (intToDecimal 0)` placeholder in the RESEARCH snippet is wrong, replace it); `sells = [ o | o <- orders, isSell o, o.limit <= pStar ]` sorted ASCENDING by limit (most-aggressive sell first — `sortOn (.limit) sells`); `buyFills = rationByPriority sortedBuys traded`; `sellFills = rationByPriority sortedSells traded`; emit `[ Allocation with desk = o.desk; side = Buy; filledQty = f | (o, f) <- buyFills ] ++ [ Allocation with desk = o.desk; side = Sell; filledQty = f | (o, f) <- sellFills ]`. Return EVERY participating eligible order (including a 0-fill or partially-filled one like C, whose residual is `order.quantity - filledQty`), so Plan 02's `Round.Clear` can mark each Order's status.

    Pitfall guards (RESEARCH Pitfalls 2 & 4): every Decimal literal carries a decimal point (`0.0`, `100.0`); keep unit quantities as `Int` end-to-end (no `Decimal` mixing in the math); use `foldl max 0` not `maximumBy`/`maximum` on a possibly-empty list.
